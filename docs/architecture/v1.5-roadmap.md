## Epic: Queue persistence (Batch + HITL)

> 正式方案 · v1.5 第 1 顺位。本节是 living spec，落地后晋升为独立 architecture 文档并在此处留链接。

### 动机

Batch (`backend/app/services/batch_service.py`) 与 HITL (`backend/app/services/hitl_queue.py`) 当前均为进程内内存状态：`BatchService.batches: Dict[str, BatchJob]` 与 `HitlReviewQueue._items: Dict[str, ReviewItem]`。服务器重启即全丢。

两者本质同构——**队列 + 状态机**：
- Batch：`BatchJob` 含 `BatchTask` 列表，状态 `pending → processing → completed/failed/skipped`，可 pause/cancel/resume/retry。
- HITL：`ReviewItem`，状态 `pending → approved/rejected`，承载人工编辑后的 `payload`。

合并为一个 epic、共用一套持久化层，避免两套并行 DB 代码与两份迁移脚本。

### 存储布局

- 单文件 SQLite：`backend/data/docuvision.sqlite`（目录加入 `.gitignore`，与 `test_data/TestResult/` 同策略）
- 两张表（按需求约束，仅两张）：
  - `batch_jobs`：一行 = 一个 BatchJob，`tasks` 以 JSON 列存储（见下方 schema）
  - `hitl_reviews`：一行 = 一个 ReviewItem
- 不引入 Redis（v1.5 不引入新中间件；SQLite 满足单机演示与投标 ETL 场景）。Redis 留作 v1.6+ 多副本运行时选项，届时抽象层切换实现即可。

### 共用抽象

新增 `backend/app/services/persistence/queue_store.py`，提供薄抽象（协议 + SQLite 实现）：

```python
class QueueStore(Protocol):
    def save(self, table: str, key: str, document: dict) -> None: ...
    def load(self, table: str, key: str) -> dict | None: ...
    def load_all(self, table: str) -> list[dict]: ...
    def delete(self, table: str, key: str) -> None: ...

class SqliteQueueStore:
    """Single-file SQLite backed implementation; JSON columns for nested fields."""
    def __init__(self, db_path: Path): ...
```

`BatchService` 与 `HitlReviewQueue` **不直接写 SQL**，各自实现两个生命周期钩子，委托 `QueueStore` 落盘：

- `load_from_db()` — 启动时从 `QueueStore.load_all()` 重建内存索引（`batches` / `_items`）
- `_persist(item)` — 每次状态变更后 upsert 单行

内存结构仍为真源运行时缓存（asyncio 锁、`_active_batches` 等运行态不落盘），DB 仅做 crash-recovery 与重启恢复。这样改动面最小：现有 `main.py` 路由与 `_process_batch` 逻辑不动，只在 `create_batch` / 状态翻转点 / `enqueue` / `resolve` 处插入 `_persist`。

### Schema

```sql
-- batch_jobs: one row per BatchJob; tasks stored as JSON array
CREATE TABLE IF NOT EXISTS batch_jobs (
    batch_id        TEXT PRIMARY KEY,
    name            TEXT NOT NULL,
    status          TEXT NOT NULL,           -- pending/processing/completed/failed/cancelled/paused
    options         TEXT NOT NULL DEFAULT '{}', -- JSON
    tasks           TEXT NOT NULL DEFAULT '[]', -- JSON array of BatchTask
    total_tasks     INTEGER NOT NULL DEFAULT 0,
    completed_tasks INTEGER NOT NULL DEFAULT 0,
    failed_tasks    INTEGER NOT NULL DEFAULT 0,
    created_at      TEXT NOT NULL,
    started_at      TEXT,
    completed_at    TEXT
);

-- hitl_reviews: one row per ReviewItem
CREATE TABLE IF NOT EXISTS hitl_reviews (
    review_id     TEXT PRIMARY KEY,
    task_id       TEXT NOT NULL,
    file_name     TEXT NOT NULL,
    reason        TEXT NOT NULL,
    payload       TEXT NOT NULL DEFAULT '{}', -- JSON; original enqueue context (validation/fields/hitl_profile)
    edited_fields TEXT,                       -- JSON; human-corrected fields written on resolve (v1.5 增量列)
    status        TEXT NOT NULL DEFAULT 'pending', -- pending/approved/rejected
    created_at    TEXT NOT NULL,
    resolved_at   TEXT
);
```

`tasks` 以 JSON 列存储是显式权衡（见 Adversarial check）。`payload` 与 `edited_fields` 分离：`payload` 保留 enqueue 时的原始 validation 上下文（不随人工编辑变化），`edited_fields` 承载 resolve 时人工修正的字段集——两者非定长，JSON 最自然。

### 重启恢复流程

1. `main.py` 启动时构造 `SqliteQueueStore(db_path=settings.SQLITE_DB_PATH)`，注入 `batch_service` 与 `hitl_queue`。
2. 各自调用 `load_from_db()`：`batch_service` 重建 `self.batches`，将 `processing` 状态的 batch 回退为 `paused`（避免重启后误以为仍在跑）；`hitl_queue` 重建 `_items`，`pending` 保持 `pending`。
3. 内存索引重建后，路由层照常工作；用户可手动 resume 暂停的 batch。
4. 后续每次 `create_batch` / `_process_batch` 内 task 状态翻转 / `pause` / `cancel` / `retry_failed_tasks` 调 `_persist(batch)`；`enqueue` / `resolve` 调 `_persist(item)`。

### 迁移与兼容

- 首次启动自动 `CREATE TABLE IF NOT EXISTS`，无需 Alembic。
- 不做内存→DB 一次性数据迁移（内存数据本就易失，无价值）；冷启动即从空表开始。
- 保留 `hitl_queue` / `batch_service` 模块级单例签名不变，路由层零改动。

### 范围内 / 范围外

- **范围内**：Batch + HITL 重启恢复、共用 SQLite 抽象、配置项、`.gitignore`。
- **范围外**：Webhook 持久化（仍内存）、多副本/Redis、Batch 任务级 SQL 查询、HITL 审计历史（只存当前态，不存编辑 diff 历史）。

### Adversarial check

- **`tasks` JSON 列写放大**：每个 task 完成都要 upsert 整个 `tasks` JSON 数组。单 batch 1000 tasks、每秒翻转 10 个 task 时，写放大与锁竞争会显现。**崩点**：单 batch 任务数 > 5000 或高并发批处理。**缓解**：届时拆出 `batch_tasks` 子表（第三张表），按 `task_id` 行级 upsert。当前两表约束以"演示/投标 ETL"规模为前提。
- **SQLite 写并发**：SQLite 单写者；`_process_batch` 并发 task 完成回调都触发 `_persist`，可能 `database is locked`。**缓解**：`SqliteQueueStore` 内部串行化写（`threading.Lock` 或 `aiosqlite` 单连接），或开启 WAL 模式（`PRAGMA journal_mode=WAL`）。方案默认开 WAL。
- **processing→paused 回退语义**：重启时把 `processing` batch 改 `paused`，但已完成的 task 结果保留。若用户不手动 resume，batch 永远停在 `paused`——这是有意为之（不自动续跑 GPU 任务），但需 UI 提示"重启后需手动 resume"。
- **HITL `payload` 增长**：`payload` 保留原始 validation 上下文（不随编辑增长），`edited_fields` 只覆盖字段。两者均不会无限增长；但若未来挂载大附件（图片 bbox 等），JSON 列体积需监控。
- **`enqueue` 改 async 的连锁**：v1.5 落地时 `HitlReviewQueue.enqueue` / `resolve` 改为 async（`_persist_async` 经 `asyncio.to_thread` 避免阻塞 event loop）。调用方仅 orchestrator `kie_step`（async）与 `main.py:resolve_hitl_review` 路由（async），已全量适配；全库搜索确认无其他调用点。
- **`SQLITE_DB_PATH` 相对路径基准**：默认 `data/docuvision.sqlite`，相对 `backend/` cwd（与 `UPLOAD_DIR=./uploads` 同基准）。若以仓库根为 cwd 启动，需用 env `DOCUVISION_SQLITE_DB_PATH` 覆盖为绝对路径，否则会在仓库根建 `data/`。
