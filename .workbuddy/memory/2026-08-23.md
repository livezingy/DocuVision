## REQ-RAG01 投标定位分析（internal-corpus-rag-citations.md）

**结论**：对"企业私有语料 + 带页码引用 RAG + 自托管 + 评测"类需求，**应从 DocuVision 切片/摄取功能来投，而不是把整个 DocuVision 当 RAG 聊天产品来投**。

**理由（与需求文档一致）**：
- DocuVision 本质是 IDP 栈（版面+OCR+表格+KIE），无检索/重排/拒答/评测能力（代码 grep 零结果）。
- envelope 已含 page_num / bbox / block_id / reading_order / confidence，是"页级块 + doc_id + page"的天然地基（已具备 80%）。
- 自托管(MIT) + 可部署客户 AWS + 数据不出域，契合合同文档不出域要求。
- 客户已被 off-the-shelf 套壳伤过；整包 DocuVision 会过度承诺、踩"套壳"红线。

**代码核对发现**：
- **DOCX 非原生输入**：DocuVision 只 export docx，不 ingest（需求要 PDF+DOCX）。
- 无 chunker / embedding / retrieval / rerank / eval 模块。

**后续改造方向（让 DocuVision 直接覆盖更多类似需求）**：
1. 新增 RAG 摄取切片模式：语义连贯块 + 稳定 chunk_id(doc_id+page+seq) + bbox + span。
2. 补 DOCX 摄取（python-docx 解析或先转 PDF）。
3. 元数据抽取层：文种(spec/contract/SOP)/日期/现行废止（扩 document_type_classifier）。
4. 引用 manifest：chunk→页裁剪图，支持"点回原页"。
5. 扫描件页码对齐鲁棒性 + ocr_status 分级。
6. 确定性 ID + 加库回归；评测沉淀为可复用 IDP 评测惯例。

## DocuVision 能力暴露形态讨论（27 份需求综合 + 对抗审查）

**背景**：综合 27 份 Upwork 需求后判断 DocuVision 当前"FastAPI 单体"形态不适合投大部分需求；用户要"像调函数/库一样便捷取用"。已确认方向 A：DocuVision 死守文档边界，工程图/科学图像单开仓。

**代码核对关键发现**：
- `packages/docuvision-core` 是独立可装包（pyproject + optional-deps 分层），但**只覆盖 Lite 表格/OCR**；Pro 的 layout/KIE/formula/seal/envelope 锁在 `backend/app/services`。
- `lite_builder.py:34` 证明 **Lite 已是"薄壳+调 core 库"范本**；Pro 照做即可（service 拆成 core纯算法 + service读配置，FastAPI 不改业务逻辑）。
- `single_file_pipeline` 是伪函数入口（7 个注入参数）；`main.py` 顶层吞 paddle/paddlex 全局单例 + `tasks:Dict` 内存字典。

**初版"积木库"思路（8块积木+三仓）**：ingest/layout/table/ocr/fields/chunk/qa/export。已自我对抗审查否决其"全做"。

**对抗审查结论（第一性）**：
1. "积木"隐喻夸大可组合性——多数需求是"输入→1-2能力→输出"，非十块拼系统。
2. 库化需复用频率支撑；PDF01 这类坐标切列 50 行脚本最优，库化收不回成本。chunk/qa 各仅 1-2 需求触发，预做违反 YAGNI。
3. 最难的"端到端胶水"（错位修正/低置信路由/校验兜底）每需求不同，积木思路漏掉。
4. 自造积木在和 Azure DI/Textract/Docling 竞争；造积木唯一理由是不可替代差异化（自托管/PaddleX+Qwen-VL 中文栈/DGX Spark 本地）。
5. 三仓(CV02/PL01/IB01 各1-2需求)是过早抽象，应塞 DocuVision 实验区等 5+ 再拆。

**修正方向（用户认可中）**：收缩到最小 SDK 4 函数（ocr/layout/fields/confidence_route）+ 云API适配层 + 脚本模板库(starter repos,非库) + 渐进库化（被3个需求调过才升级正式SDK）。复用资产不止代码：Demo产物/方案模板/golden set 评测集同等重要。

## 三条技术深挖结论（对抗审查续）

1. **胶水复用做"可拷贝模板"不做SDK**：骨架(checksum_gate状态机/route阈值/golden fixture加载)可复用，语义每需求不同；形态=`templates/xxx/`骨架py + README写"语义怎么填"，新单 `cp -r` 改不 `import`。

2. **表格准确率靠"锚点+降级链"不靠自适应参数**：PDF01实测 `pdfplumber.find_tables()` 无ruling返回1列整页，调参救不回。优先 `extract_words()` 坐标 + 语义锚点(Log ID/单号作记录起点重置)；无文本层才上视觉(PP-Structure > Camelot > find_tables)；变长行用唯一键探测；跨页用唯一键重置。自适应参数过拟合样例。

3. **OCR靠混合路由不靠单一引擎优化**：印刷→PaddleOCR/Azure，手写/隐私/疑难→Qwen本地，按置信度路由切换。Tesseract只作零依赖兜底，不为之做预处理（预处理对印刷有效对手写无效，PaddleOCR自带更强）。Qwen本地vs Azure成本：日处理>~6000页且GPU利用率>50%时本地略优；真正优势是数据不出境+无限并发+手写准确率，非纯成本。

三条同向结论：**别在弱环节贴补丁，把弱环节降为兜底、强环节做透、中间用路由胶水连起来**。
