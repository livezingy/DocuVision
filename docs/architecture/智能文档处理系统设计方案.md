# 智能文档处理系统设计方案

> 版本：v0.8  
> 日期：2026-04-03  
> 参考：Azure Document Intelligence Layout API（layout-checklist.jpg.json 等样本）

---

## 1. 系统目标

基于 PaddleX 套件，构建一套对标 Azure Document Intelligence 的智能文档处理系统，具备以下特征：

- **默认通用**：OCR 文本、版面解析、表格、图像区域提取开箱即用
- **按需增强**：公式识别、印章识别、证件/票据字段提取作为可选插件
- **数据分层**：原始数据、融合数据、展示数据三层独立保留
- **可扩展**：架构统一，印章/公式/证件等后续类型无需改动核心流程

---

## 2. 核心引擎选型

| 能力 | 引擎 | 默认/可选 |
|---|---|---|
| 文档预处理（纠偏/旋转/去扭曲） | `doc_preprocessor` | 默认 |
| 版面解析（区域检测与分类） | `PP-StructureV3` | 默认 |
| 文本 OCR | `PaddleOCR`（对文本白名单块执行 per-block OCR） | 默认 |
| 表格识别 | `PP-StructureV3` 内置 `TableRecognitionV2` | 默认 |
| 图像/图表区域提取 | `PP-StructureV3` layout block | 默认 |
| 公式识别 | `formula_recognition` | 可选 |
| 印章识别 | `seal_recognition` | 可选 |
| 证件/票据字段提取 | `PP-ChatOCRv4-doc` / `doc_understanding` | 可选 |
| 文档翻译 | `PP-DocTranslation` | 可选 |

**核心策略：PP-StructureV3 做结构真相（版面、区域类型、坐标），PaddleOCR 做文本真相（空格、字符串），融合构建前端可用数据。**

> PP-StructureV3 存在多行文本词间空格丢失的问题，因此使用 PaddleOCR 对文本白名单 block 单独重新识别。文本替换采用统一策略：标题/正文核心类型始终优先 OCR，其余文本类型按置信度与长度比规则兜底。坐标（bbox/polygon）始终保留 PP-StructureV3 的结果。

## 3. 坐标系统设计

处理流程中存在两个关键坐标空间：

```
原图坐标空间 (original)
       ↓  预处理正变换（旋转 + 可选去扭曲）
预处理图坐标空间 (preprocessed)   ← PP-StructureV3 与 PaddleOCR 共同输入
       ↓  按 block bbox 裁剪
block 局部坐标空间 (crop)         ← PaddleOCR per-block 输入（坐标不用于展示）
```

### 3.1 双坐标模式（部署时配置，启动后固定）

**`use_doc_unwarping` 是服务配置项（`backend/config/settings.py`），与 `DEBUG_MODE` 同属部署层，在服务启动时确定，对所有请求生效，不是逐图自动检测的结果。**

> **源码确认（`doc_preprocessor/pipeline.py`）：** `use_doc_unwarping` 在 `__init__` 决定是否加载 UVDoc 权重；`predict()` 层面只判断是否执行，执行时对每张图无条件跑 UVDoc，没有任何"是否需要校正"的自动判断逻辑。

后端根据该配置值写入 `preprocessing.coordinate_space`，前端读取后无需关心底层逻辑：

| `use_doc_unwarping`（服务配置） | 坐标处理 | view 层坐标空间 | 前端展示图像 |
|---|---|---|---|
| `False` | 旋转逆矩阵 → 还原到原图 | `"original"` | `original_image`（原始上传图） |
| `True` | 无逆变换，直通 preprocessed | `"preprocessed"` | `preprocessed_image`（分析图） |

**适用场景参考：**
- `use_doc_unwarping=True`：扫描仪扫描、可能存在透视形变的文档
- `use_doc_unwarping=False`：数字原生 PDF、已端正的图像，坐标可精确还原

两种情况下前端叠加逻辑完全相同：
```
if preprocessing.coordinate_space == "original":
    显示 original_image，polygon 直接叠加
else:
    显示 preprocessed_image，polygon 直接叠加
```

差异只在显示哪张图；polygon 的叠加代码路径完全一致。

### 3.2 use_doc_unwarping=False：旋转逆矩阵 → original 坐标

仅包含旋转纠正（0/90/180/270°）时，变换可精确求逆，view 层坐标还原到原图空间：

```python
import cv2
import numpy as np

def get_rotation_inverse_matrix(original_hw, angle):
    """
    给定原图 (h, w) 和旋转角度（0/90/180/270），返回逆变换 2×3 仿射矩阵。
    仅在 use_doc_unwarping=False 时可以精确还原到 original 坐标。
    """
    h, w = original_hw
    center = (w / 2, h / 2)
    mat = cv2.getRotationMatrix2D(center, angle, 1.0)
    cos = np.abs(mat[0, 0])
    sin = np.abs(mat[0, 1])
    new_w = int(h * sin + w * cos)
    new_h = int(h * cos + w * sin)
    mat[0, 2] += (new_w - w) / 2
    mat[1, 2] += (new_h - h) / 2
    inv_mat = cv2.invertAffineTransform(mat)
    return inv_mat, (new_w, new_h)

def apply_inverse_rotation(points, inv_mat):
    pts = np.array(points, dtype=np.float64)
    pts_h = np.hstack([pts, np.ones((len(pts), 1))])
    return (inv_mat @ pts_h.T).T.tolist()
```

`view_builder.py` 在构建 view 层时调用此函数，将 fused 层所有 block 的 polygon 坐标一次性转换到 original 空间。

### 3.3 use_doc_unwarping=True：直通 preprocessed 坐标

`DocUnwarping`（UVDoc）是深度神经网络，输出仅为像素结果（源码 `pipeline.py`：`item["doctr_img"]` 直接取像素），**无变换矩阵，无法精确求逆**。此时 view 层直接使用 preprocessed 坐标，前端展示 `preprocessed_image`，坐标与展示图像完全对齐，零误差。

### 3.4 预处理选项汇总

预处理由 `doc_preprocessor` 子 pipeline 提供，包含以下可选开关：

| 参数 | 可选值 | 坐标可逆性 | 说明 |
|---|---|---|---|
| `use_doc_preprocessor` | `True / False` | — | 总开关 |
| `use_doc_orientation_classify` | `True / False` | ✅ 精确可逆（仿射逆矩阵） | 旋转纠正，仅支持 0/90/180/270° |
| `use_doc_unwarping` | `True / False` | ❌ 不可逆（UVDoc 神经网络） | 透视/扭曲校正 |

### 3.5 预处理模块输出

`coordinate_space` 由后端根据 `use_doc_unwarping` 自动写入，前端只读不写：

```json
// use_doc_unwarping=false 时
"preprocessing": {
  "input_size": [4000, 3000],
  "output_size": [3000, 4000],
  "use_doc_orientation_classify": true,
  "use_doc_unwarping": false,
  "angle_deg": 90,
  "coordinate_space": "original"
}

// use_doc_unwarping=true 时
"preprocessing": {
  "input_size": [3000, 4000],
  "output_size": [2580, 3433],
  "use_doc_orientation_classify": true,
  "use_doc_unwarping": true,
  "angle_deg": 270,
  "coordinate_space": "preprocessed"
}
```

## 4. 后端处理流水线

```
原始文档输入（PDF / JPG / PNG）
        │
        ▼
┌─────────────────┐
│   文档预处理     │  输出 preprocessed_image + 预处理参数（angle_deg/use_doc_unwarping 等）
└────────┬────────┘
         │ 同一张 preprocessed_image（内部 preprocessor 已关闭）
         ▼
    PP-StructureV3
         │
         ▼
  按 block.type 分类（BLOCK_LABEL_MAP 白名单）
         │
         ├── vision_labels（table/image/chart/figure/flowchart）→ 直接保留
         ├── type = formula →  （可选）裁剪 → formula_recognition
         ├── type = seal    →  （可选）裁剪 → seal_recognition
         └── text 类（doc_title/paragraph_title/text/header/footer/footnote 等）
                   │
                   ▼
             裁剪 block bbox 区域（从 preprocessed_image）
                   │
                   ▼
             PaddleOCR（per-block，单独识别）
                   │
                   ▼
             多行文本拼接 → block.text
                   │
                   ▼
             写入 fused 层（bbox 来自 PP-StructureV3，text 来自 OCR）
         │
         ▼
  全部 blocks 汇总，直接构建 view 层
         │
         ▼
  构建 view 层（坐标空间由 settings.USE_DOC_UNWARPING 决定：False → original，True → preprocessed）
```

### 4.1 PaddleOCR 的处理范围

**结论：裁剪文本白名单 block（而非仅 `text`），单独送 PaddleOCR，不做整页 OCR。**

理由：
- PP-StructureV3 已将 text 与 table 区域分离，天然排除了表格干扰
- 无需复杂的空间 overlap 匹配与冲突消解逻辑
- OCR 在小区域精度更高、无交叉干扰
- OCR 坐标完全不用于显示，不需要任何坐标对齐处理

### 4.2 预处理对齐（关键）

**源码发现：PP-StructureV3 与 OCR pipeline 的 `use_doc_preprocessor` 默认值不同：**

| Pipeline | `use_doc_preprocessor` 默认值 |
|---|---|
| `OCR.yaml` | **`True`** |
| `PP-StructureV3.yaml` | **`False`** |

必须通过以下方式之一确保两引擎输入同一张图：

**推荐方式（外部统一预处理）：**
1. 外部调用 `doc_preprocessor` 得到 `preprocessed_image`
2. 将 `preprocessed_image` 分别传入 PP-StructureV3 和 PaddleOCR
3. 两者均关闭内部 `use_doc_preprocessor`（设为 `False`）

**备选方式：**
- 设置 PP-StructureV3 的 `use_doc_preprocessor: True`，确保两个 pipeline 使用相同预处理配置
- 风险：两个 pipeline 各自独立运行预处理，若随机性影响结果会引入不一致

## 5. 文本替换规则

### 5.1 替换范围

PP-StructureV3 默认使用 `PP-DocLayout_plus-L`（20类）。以下为各类型的处理策略，以 `BLOCK_LABEL_MAP` 分组为依据：

| block.type | 分组 | 送 OCR | 显示 bbox | 显示 text |
|---|---|---|---|---|
| `doc_title` | doc_title_labels | ✅ | PP-StructureV3 | OCR 拼接文本 |
| `paragraph_title` | paragraph_title_labels | ✅ | PP-StructureV3 | OCR 拼接文本 |
| `abstract_title` / `reference_title` / `content_title` | paragraph_title_labels（仅25类模型） | ✅ | PP-StructureV3 | OCR 拼接文本 |
| `text` | text_labels | ✅ | PP-StructureV3 | OCR 拼接文本 |
| `abstract` / `content` / `reference` / `reference_content` | text_labels 扩展 | ✅ | PP-StructureV3 | OCR 拼接文本 |
| `algorithm` | text_labels 扩展 | ✅ | PP-StructureV3 | OCR 拼接文本 |
| `header` / `header_image` | header_labels | ✅ | PP-StructureV3 | OCR 拼接文本 |
| `footer` / `footer_image` / `footnote` | footer_labels | ✅ | PP-StructureV3 | OCR 拼接文本 |
| `figure_table_chart_title` | vision_title_labels | ✅ | PP-StructureV3 | OCR 拼接文本 |
| `aside_text` | unordered_labels | ✅ | PP-StructureV3 | OCR 拼接文本 |
| `number` / `formula_number` | unordered_labels | ⚠️ 可选，通常极短 | PP-StructureV3 | OCR 或原文 |
| `table` | vision_labels | ❌ | PP-StructureV3 | PP-StructureV3 原始（cells/HTML） |
| `image` / `chart` / `figure` / `flowchart` | vision_labels | ❌ | PP-StructureV3 | 无 |
| `formula` / `inline_formula` | — | ❌ | PP-StructureV3 | formula_recognition 结果（可选） |
| `seal` | unordered_labels | ❌ | PP-StructureV3 | seal_recognition 结果（可选） |

> **实现建议：** 使用 `BLOCK_LABEL_MAP` 中各分组的并集作为"送 OCR 白名单"，自动兼容 PP-DocLayout_plus-L（20类）和 PP-DocLayoutV3（25类）两种模型。

### 5.2 多行文本拼接策略

对裁剪块运行 OCR 后，按以下规则拼接多条 lines：

1. 按 line 的 y 中心坐标升序排列（阅读顺序）
2. 判断行间距：
   - `line_gap < 1.2 × font_height` → 同段落，连接方式按上下文选择换行 `\n` 或空格
   - `line_gap ≥ 1.2 × font_height` → 段落分隔，插入 `\n\n`
3. 行内词间空格直接使用 OCR `line.text` 原始值，不做额外拼接

**段落的 bbox/polygon 始终使用 PP-StructureV3 的 block 框，不使用 OCR 行框合并结果。**

### 5.3 OCR 替换策略（统一策略映射）

系统按 block.type 执行两类策略：

- `always_replace`：有 OCR 文本即替换（无 OCR 才回退）
- `guarded_replace`：仅在置信度与长度比通过时替换

当前 `always_replace` 类型：

`text`、`paragraph_title`、`abstract_title`、`reference_title`、`content_title`、`figure_table_chart_title`、`abstract`、`content`、`reference`

其余文本白名单类型使用 `guarded_replace`（如 `reference_content`、`header`、`footer`、`aside_text`、`number` 等）。

### 5.4 OCR 兜底状态

| 条件 | `replace_status` | 处理 |
|---|---|---|
| OCR 正常 | `replaced` | 使用 OCR 文本 |
| OCR 返回空 | `no_match` | 保留 PP-StructureV3 原始文本 |
| OCR 平均 confidence < 0.6 | `low_confidence` | 保留原始文本，标记警告 |
| OCR 输出长度 < PP-StructureV3 文本的 50% | `suspicious` | 保留原始文本，记录两侧对比 |
| block.type = table | `skip_table` | 不参与替换 |

### 6.5 三层差异对比与注意事项

#### 6.5.1 整体差异对比

| 维度 | raw 层 | fused 层 | view 层 |
|---|---|---|---|
| **受众** | 内部存储/重处理 | 调试/溯源 | 前端消费/用户下载 |
| **结构形态** | 两个引擎输出并排存储，格式各异 | 按 block 合并的统一结构，扁平列表 | 以消费者为中心重组，有文档级聚合数组 |
| **坐标空间** | preprocessed（引擎直接输出） | preprocessed（始终，与配置无关） | original 或 preprocessed（由 `USE_DOC_UNWARPING` 决定） |
| **text 类文本** | PP-StructureV3 原文（可能空格丢失）+ OCR 原始结果各存一处 | OCR 拼接文本（含兜底逻辑决策结果） | 同 fused，但去除了 provenance |
| **table/figure** | PP-StructureV3 原始结构 | payload 规范化 + `processing_status` | 同 fused payload，加 `crop_image_url` 等前端字段 |
| **融合决策信息** | 无 | `processing_status` + `provenance`（structure_text vs ocr_lines 对比） | 保留 `processing_status`，丢弃 `provenance` |
| **文档级聚合** | 无 | 无 | 有 `paragraphs[]`、`tables[]`、`figures[]`、`formulas[]`、`seals[]`、`fields{}` |
| **字段命名** | 引擎原生字段名 | `block_id`、`type`、`bbox_preprocessed`、`polygon_preprocessed` | `id`、`kind`、`polygon`（无 `_preprocessed` 后缀） |
| **生命周期** | 调试模式下写盘；生产模式下仅内存中转 | 同 raw | 始终存在于 API 响应；生产唯一对外层 |

#### 6.5.2 view_builder.py 的职责边界

`view_builder.py` 是唯一在 fused → view 转换中做以下事情的地方：

1. **坐标变换**（唯一允许发生坐标转换的地方）：`USE_DOC_UNWARPING=False` 时调用 `apply_inverse_rotation()`，将所有 block 的 `polygon_preprocessed` 一次性转换为 original 坐标
2. **字段重命名**：`block_id`→`id`、`type`→`kind`、`polygon_preprocessed`→`polygon`、`width_preprocessed`→`width`
3. **丢弃调试信息**：`provenance`、`crop_offset`、`bbox_preprocessed` 不写入 view
4. **文档级聚合**：从 `pages[].elements` 聚合出 `tables[]`、`paragraphs[]`、`figures[]` 等跨页数组

**严禁在 fusion.py 或引擎适配层中做坐标变换**；fused 层的 `_preprocessed` 后缀字段名是对这一约束的显式提醒。

#### 6.5.3 各层注意事项

**raw 层：**
- `raw.pp_structure_v3` 保留 PP-StructureV3 的原生输出格式（不做任何规范化），供需要重新 fusion 时直接重放
- `raw.paddleocr_blocks` 是以 block_id 为键的字典，每条记录含 OCR 的原始 `lines`（含 `crop_polygon` 和原始置信度）
- 生产模式下 raw 层**不持久化、不返回 API**；调试模式下写入 `backend/debug/{job_id}/raw_*.json`

**fused 层：**
- `bbox_preprocessed` 字段是 `[x_min, y_min, x_max, y_max]` 轴对齐矩形；`polygon_preprocessed` 是四点多边形，两者均来自 PP-StructureV3，**在任何配置下都不做逆变换**
- `provenance` 字段仅在 `processing_status` 为 `replaced`/`low_confidence`/`suspicious`/`no_match` 时有实际价值；`skip_table` 时为 `null`
- 新增引擎类型时，只扩展 `payload` schema，`block_id`/`type`/`bbox_preprocessed`/`polygon_preprocessed`/`processing_status`/`source`/`confidence`/`provenance` 八个公共字段**不允许改动**

**view 层：**
- `pages[].width` / `pages[].height` 的含义随 `coordinate_space` 变化：`"original"` 时为原图尺寸，`"preprocessed"` 时为预处理图尺寸；前端在渲染时需以此为归一化基准
- `polygon` 坐标为 8 个整数 `[x1,y1,x2,y2,x3,y3,x4,y4]`（四点顺时针），前端渲染框时直接连线
- `view.tables[]` / `view.paragraphs[]` 等文档级数组是 `pages[].elements` 的**引用投影**，不是独立副本；序列化时需注意避免出现既有 `elements` 又有重复数据的冗余

## 9. 前端展示规范

### 9.1 数据消费约定

- 前端默认只读 **view 层**，不直接消费 fused 或 raw
- 文本渲染：`view.pages[].elements[kind=text/title/paragraph].payload.text`
- 表格渲染：`view.pages[].elements[kind=table].payload.html` 或 `cells`
- 坐标渲染：`view.pages[].elements[].polygon`（坐标空间由 `preprocessing.coordinate_space` 决定；叠加到对应展示图像上，逻辑与坐标空间无关）
- 字段渲染：`view.fields`（文档级 KIE 结果）

### 9.2 建议的前端 Tab 结构

| Tab | 数据来源 |
|---|---|
| Overview | `quality` + `preprocessing` |
| Text | `view.paragraphs` + `view.pages[].content` |
| Tables | `view.tables`（cells + HTML 预览 + 导出） |
| Figures | `view.figures` |
| Fields | `view.fields` |
| Raw JSON | 完整 Envelope |

### 9.3 调试模式（服务级开关）

**调试模式使用服务级开关（config / 环境变量），而非每次请求参数。**

原因：
- 生产环境永远不应将 `raw`/`fused` 写盘，避免磁盘 I/O 和内部数据暴露
- 开发/测试环境希望每次请求自动落档，不依赖调用方主动声明
- 若允许请求级 `"debug": true`，会引入权限管理问题（任意调用者可获取内部中间数据）

**配置方式（`backend/config/settings.py` 或 `.env`）：**

```python
DEBUG_MODE = False            # 环境变量 APP_DEBUG_MODE 覆盖
DEBUG_OUTPUT_DIR = "backend/debug"
DEBUG_KEEP_LAST_N = 50        # 最多保留最近 50 个 job 的调试文件，超出自动清理
USE_DOC_UNWARPING = True      # 环境变量 APP_USE_DOC_UNWARPING 覆盖；决定坐标策略
```

**云端调试建议：**

- 仓库跟踪 `backend/.env.cloud` 作为非敏感模板（默认可设置 `OCR_LANG=en`）
- 运行 `backend/run.py` 时，若 `backend/.env` 不存在且 `backend/.env.cloud` 存在，启动脚本会自动复制模板为 `.env`
- 真实私密配置保持在本地 `.env`，不提交到仓库

**调试文件目录结构（`DEBUG_MODE=true` 时每个 job 自动生成）：**

```
backend/debug/
  {job_id}/
    original_image.jpg           # 原始上传图（始终保存，便于与 preprocessed 对比）
    preprocessed_image.jpg       # 送入引擎的图（始终保存）
    raw_pp_structure_v3.json     # PP-StructureV3 原始输出
    raw_paddleocr_blocks.json    # 各 block 的 PaddleOCR 原始输出
    fused.json                   # fused 层完整数据（含 provenance）
    quality.json                 # quality 层
```

> `view` 层不写入 debug 文件夹；它是用户可见层，由 API 响应返回。

**两种模式下的数据可见性：**

| 模式 | API 响应包含 | 磁盘写入 |
|---|---|---|
| 生产（`DEBUG_MODE=false`） | `view` + `quality` + `preprocessing` | 无 |
| 调试（`DEBUG_MODE=true`） | 同上，不额外暴露 raw/fused | `backend/debug/{job_id}/` |

调试数据通过独立端点访问，不混入正常响应：

```
GET /api/v1/jobs/{job_id}/debug
```

此端点仅在 `DEBUG_MODE=true` 时可用，否则返回 `404`。前端调试 Tab（Raw JSON）在生产模式下可隐藏或仅展示 view 层内容。

### 9.4 可视化与下载 JSON 一致性约定

**前端可视化与用户下载的 JSON 必须完全一致，通过架构强制保证，而非靠约定：**

- **view 层是唯一数据源**：前端渲染和 JSON 下载均读取同一 `view` 层，不允许前端自行从 `fused`/`raw` 合成展示数据
- **标准下载**：默认下载内容 = `analyzeResult.view` 序列化（Azure 风格，去掉 raw/fused）
- **调试下载**：完整 Envelope（raw + fused + view），供开发调试
- **坐标一致**：标注框 polygon 与 JSON 中 polygon 字段完全相同；坐标空间由 `preprocessing.coordinate_space` 标注，前端读取该字段决定展示哪张图

## 11. 关键设计原则汇总

| 原则 | 决策 |
|---|---|
| OCR 范围 | 裁剪文本白名单 block（`_OCR_TEXT_LABELS` 全集），不整页 OCR |
| 坐标来源 | 所有展示坐标来自 PP-StructureV3 |
| 坐标空间 | `settings.USE_DOC_UNWARPING=False` → 旋转逆矩阵 → original 坐标；`True` → 直通 preprocessed 坐标；由 `coordinate_space` 字段通知前端 |
| 段落 bbox | 始终用 PP-StructureV3 block bbox |
| 段落文本 | OCR 多行拼接，行间距决定换行/合并 |
| 表格 | 绝对不送 OCR，完整保留 PP-StructureV3 结果 |
| 前端字段 | view 层字段即渲染字段；读取 `preprocessing.coordinate_space` 选择展示图像，坐标叠加逻辑统一 |
| 调试模式 | 服务级开关（`DEBUG_MODE` 环境变量），开启后自动写 `backend/debug/{job_id}/`，不混入 API 响应 |
| 兜底 | OCR 空/低置信/输出异常时，保留 PP-StructureV3 原文 |
| 扩展方式 | block 引擎注册表 + payload 多态 + 开关预留 |
